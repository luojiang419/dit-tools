# 逐帧解析尾部漏帧原因与修复方案

日期：2026-07-30

## 一、任务目标

定位素材管理中心“逐帧解析”区域在视频尾部缺少抽帧结果的原因，并设计一套满足以下条件的修复方案：

1. 固定间隔抽帧仍保持现有采样语义和成本上限。
2. 任意非空视频都覆盖第一帧和最后一帧。
3. 逐帧模式不重复、不漏掉最后一帧。
4. 旧解析结果可以按需补齐尾帧，不强制全量重新解析。
5. 界面准确显示帧时间，避免把几百毫秒误看成整秒。
6. CFR、VFR、非整除帧数、短视频和容器/视频流时长不一致时均可验证。

## 三、证据与根因

### 3.1 真实任务没有在中间链路丢帧

对当前本机数据库、缓存文件和原视频进行只读核对：

| 样本 | 总时长 | 视频流 | 采样间隔 | 源帧数 | 计划数 | 数据库数 | 有效图片 | 成功数 | 最后采样帧/时间 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Anine bing jeans campaign SS2025.mp4 | 21.056s | 60fps / 21.000s | 15 | 1260 | 84 | 84 | 84 | 84 | 1246 / 20.750s |
| Bouthentique Summer 2025…mp4 | 58.516s | 25fps / 58.480s | 15 | 1462 | 98 | 98 | 98 | 98 | 1456 / 58.200s |

两条任务均满足：

```text
计划帧数 = 数据库帧数 = 有效缓存图片数 = 视觉解析成功数
```

因此不是 FFmpeg 运行失败、数据库漏写、模型跳过或界面查询少取造成的随机漏帧。

### 3.2 固定间隔计划没有“尾帧必须覆盖”约束

当前规则：

```cpp
for (int zeroBased = 0; zeroBased < count; zeroBased += interval) {
    numbers.append(zeroBased + 1);
}
```

抽帧层使用同样的模运算：

```cpp
if ((index % interval) != 0) {
    continue;
}
```

所以只有当：

```text
(sourceFrameCount - 1) % frameInterval == 0
```

时最后一帧才会刚好入选。

真实样本一：

```text
源帧数：1260
间隔：15
现有序列：1, 16, 31, ..., 1246
未覆盖尾帧：1247..1260，共 14 帧
最后采样 PTS：20.750s
最后可解码帧 PTS：20.983s
封装总时长：21.056s
```

真实样本二：

```text
源帧数：1462
间隔：15
现有序列：1, 16, 31, ..., 1456
未覆盖尾帧：1457..1462，共 6 帧
最后采样 PTS：58.200s
最后可解码帧 PTS：58.440s
封装总时长：58.516s
```

这属于采样计划的边界覆盖缺失，不是执行过程中的随机丢帧。

### 3.3 时间显示把几百毫秒放大成了“一整秒”

逐帧卡片当前复用了 `Formatters::formatDuration()`：

```cpp
const qint64 totalSeconds = durationMs / 1000;
```

这是向下截断，不显示毫秒。20.750 秒显示为 `0:20`，21.056 秒显示为 `0:21`，用户看到的标签像是尾部整整空了一秒，但真实封装时长差是 306 毫秒。

这个复用还有一个附带问题：时间戳 0 是合法首帧时间，但 `formatDuration(0)` 会显示“未知时长”。

### 3.4 封装总时长不等于视频流最后一帧时间

样本一：

```text
封装时长：21.056s
视频流时长：21.000s
最后帧 PTS：20.983s
```

样本二：

```text
封装时长：58.516s
视频流时长：58.480s
最后帧 PTS：58.440s
```

最后一帧 PTS 加一帧持续时间才到达视频流末端；容器还可能包含音频尾巴或封装舍入。因此验收目标不能定义为“在封装 duration 的精确时刻生成一张帧”，而应定义为“计划中必须包含 ffprobe 枚举到的最后一张可解码视频帧”。

### 3.5 命名造成模式误解

界面区域统一叫“逐帧解析”，但真实任务计划记录的是 `frame_interval = 15`。该区域展示的是“抽取出来的帧的逐帧分析结果”，不等于设置中的 `EveryFrame` 模式。界面没有显示本次结果采用的采样规则，容易把“每 15 帧抽 1 帧”误认为“原视频每一帧都已解析”。

## 四、推荐方案

### 4.1 采样不变量：固定间隔并强制首尾覆盖

把统一采样计划定义为：

```text
N = sourceFrameCount
I = max(1, frameInterval)

N == 0：空计划
N > 0：先生成 1, 1+I, 1+2I, ...
若最后一个计划帧不是 N，再追加 N
```

设计伪代码：

```cpp
QVector<int> plannedFrameNumbers(int sourceFrameCount, int frameInterval)
{
    QVector<int> numbers;
    const int count = qMax(0, sourceFrameCount);
    const int interval = qMax(1, frameInterval);
    if (count == 0) {
        return numbers;
    }

    for (int zeroBased = 0; zeroBased < count; zeroBased += interval) {
        numbers.append(zeroBased + 1);
    }
    if (numbers.last() != count) {
        numbers.append(count);
    }
    return numbers;
}
```

性质：

- 间隔 1：仍为 `1..N`，不重复追加。
- 间隔大于 1：最多增加一张图和一次模型调用。
- 不依赖帧率、时长或 CFR/VFR，直接以 ffprobe 实际枚举结果为准。
- 短视频、非整除帧数、VFR 均有确定行为。

### 4.2 让计划层成为唯一规则来源

`FFmpegAdapter::extractFrames()` 当前自行用 `% interval` 再实现一次计划规则。修复时不能只改 `plannedFrameNumbers()`，否则尾帧会出现在“期望计划”中，却仍被抽帧层的模运算过滤。

推荐流程：

```cpp
const auto plannedNumbers =
    VisualAnalysisMetadata::plannedFrameNumbers(frames.size(), result.frameInterval);
const QSet<int> plannedSet(plannedNumbers.cbegin(), plannedNumbers.cend());

for (int index = 0; index < frames.size(); ++index) {
    const int frameNumber = index + 1;
    if (!plannedSet.contains(frameNumber)) {
        continue;
    }
    if (!requestedFrameNumbers.isEmpty()
        && !requestedFrameNumbers.contains(frameNumber)) {
        continue;
    }
    // 生成 ExtractedFrame
}
```

这样初次抽帧、计划校验、缺帧修复和完成度判断都使用同一套规则，不会再次出现边界定义漂移。

### 4.3 旧结果采用“按需补一帧”，不自动产生批量接口费用

现有数据已经保存 `source_frame_count`、`frame_interval` 和所有帧号。统一计划函数改动后：

1. `hasIncompleteVisualFrames()` 会把缺少的最后一帧识别为未完成。
2. 用户再次对同一素材执行解析，若采样间隔未改变，走 Resume。
3. `missingCacheFrames` 只包含尾帧。
4. 只抽取、调用模型并写入这一帧。
5. 已成功帧保持不变，然后重新生成汇总。

不建议升级后自动重跑全部历史视频，因为会在用户不知情时产生视觉接口费用。建议提供两个入口：

- 单素材：现有“继续/解析”入口自动判断并补齐。
- 批量：用户主动选择“补齐旧解析尾帧”，先显示预计素材数和新增模型调用次数。

如果解析间隔已经变化，则保持现有行为，明确提示将按新规则重建计划，避免把“补尾帧”伪装成低成本续跑。

### 4.4 帧时间使用独立格式化函数

不要修改通用 `formatDuration()` 的全部调用方，新增帧时间专用接口，例如：

```cpp
QString Formatters::formatFrameTimestamp(qint64 timestampMs);
```

规则：

- `< 0`：`未知时间`
- `0`：`0:00.000`
- 其余：`H:MM:SS.mmm` 或 `M:SS.mmm`

逐帧卡片改用该函数。帧率较高时毫秒必须保留三位，否则 60fps 的多帧会显示成同一个时间。

### 4.5 界面显示真实采样规则

建议把区域标题从单独的“逐帧解析”调整为：

```text
抽帧解析
当前结果：每 15 帧抽 1 帧 · 首尾必含 · 共 85 帧
```

若设置为 `EveryFrame`：

```text
当前结果：逐帧解析 · 共 1260 帧
```

注意应显示结果计划中持久化的 `frame_interval`，而不是只读当前设置；当前设置可能已在解析完成后改变。

### 4.6 抽帧完成后的防回归校验

在抽帧结果返回前增加不变量检查：

```text
sourceFrameCount > 0
frames 非空
frames.first.frameNumber == 1
frames.last.frameNumber == sourceFrameCount
每个 imagePath 都存在且 size > 0
帧号严格递增且不重复
时间戳非递减
```

仅修复缺失帧的请求则校验：

```text
返回帧号集合 == requestedFrameNumbers 与统一计划的交集
```

错误信息应同时包含源帧数、间隔、首尾计划帧号和实际返回数，便于下一次直接定位。

## 七、验收标准

1. 对任意 `sourceFrameCount > 0`，持久化计划的第一帧号为 1，最后帧号等于 `sourceFrameCount`。
2. `EveryFrame` 模式下计划数严格等于源帧数，帧号连续且无重复。
3. 固定/自定义间隔模式最多比旧算法增加一帧。
4. 每个计划帧都有有效图片和数据库行；成功模型解析后有对应成功状态。
5. 旧同间隔计划补齐时只处理缺失尾帧，不重跑已成功帧。
6. 逐帧卡片显示毫秒，0ms 不再显示“未知时长”。
7. 界面明确区分“逐帧模式”和“固定间隔抽帧结果”。
8. 当前两个真实样本分别以第 1260、1462 帧结尾。
9. 全量单元测试、FFmpeg 集成测试、Release 构建和启动探针通过。

## 九、结论

当前现象是两个问题叠加：

1. 固定间隔采样没有把“最后一帧必须入选”作为不变量，尾部最多会缺少 `frameInterval - 1` 个源帧的代表图。
2. 帧时间按整秒向下截断，把约 0.3 秒的真实尾部空档显示成 `0:20` 对 `0:21`，造成“漏了整整一秒”的观感。

推荐采用“固定间隔 + 强制首尾覆盖”的最小修复，并让所有抽帧、修复和完成度检查共用唯一计划函数。这样成本最多增加一帧，同时能从根本上消除尾部无代表帧的问题。
