5. 更新器固定 600 秒总下载时限、没有断点续传、没有旧包清理和磁盘空间预检。当前 v0.1.177 安装包约 732 MiB，本机更新缓存已经实际累积到 **5.079 GiB / 5708 个文件**。
6. 官网线上下载清单仍为 v0.1.150，而 GitHub Latest Release 已为 v0.1.177；按官网入口下载会落后 27 个补丁版本。
7. 多个 `QtConcurrent::run([this])` 任务未保存 future、未在退出时等待，自动安装触发应用退出时尤其容易撞上对象生命周期、数据库连接和后台写入问题。

## 3. P0 严重问题

### P0-01 反馈服务使用公网明文 HTTP，令牌进入 URL

**类型：已确认的线上隐私和会话安全问题。**

现象与证据：

- `FeedbackService.cpp:30` 固定使用 `http://115.231.35.105:3021/`。
- `FeedbackService.cpp:370-374`、`587-591`、`636-640` 把 `client_token` 放在查询参数中。
- `services/feedback/server/app/main.py:194`、`958-980` 把客户端和管理员 WebSocket 令牌放在 URL 查询参数中。
- `FeedbackService.cpp:816-851` 把客户端令牌写入 `QSettings` JSON。
- 线上只读验证：`http://115.231.35.105:3021/health` 返回 HTTP 200，说明生产入口当前确实是明文公网服务。

可见后果：

- 同网络、代理、网关、恶意热点或链路中间人可读取反馈正文、联系方式、系统信息、项目名称、项目路径和附件。
- URL 中的令牌可能进入代理日志、访问日志、诊断工具和错误报告。
- 客户端令牌泄露后，可读取消息、发送消息、删除消息或清空会话。
- 管理员令牌泄露后，影响全部反馈会话。

立即止血：

1. 暂停公网直连端口，改为受控域名的 HTTPS/WSS 反向代理。
2. 轮换生产管理员密码、现有管理员令牌和客户端会话令牌。
3. 客户端 REST 鉴权改用 `Authorization` 头；WebSocket 若只能用查询参数，必须建立在 WSS 上并避免记录完整 URL。
4. 对日志、错误页面和代理配置做令牌脱敏。

验收标准：

- 抓包中没有任何明文反馈内容或令牌。
- HTTP/WS 被拒绝或强制跳转到 HTTPS/WSS。
- 历史令牌全部失效。
- 服务器访问日志不保存完整鉴权查询参数。

### P0-02 未校验内容和发布者的安装包会被 UAC 提权执行

**类型：已确认的供应链与本地提权风险。**

现象与证据：

- `UpdateService.cpp:187-234` 只读取版本、安装包名称、URL 和大小，没有读取 GitHub asset digest 或 `.sha256`。
- `UpdateService.cpp:667-694` 对 pending 只验证路径存在和文件名。
- `UpdateService.cpp:697-723` 复用缓存时只比较大小。
- `UpdateService.cpp:962-1001` 下载完成后只检查非空和大小，然后重命名为正式安装包。
- `UpdaterSession.cpp:453` 通过 PowerShell `Start-Process -Verb RunAs` 以管理员权限执行该文件。
- `.github/workflows/release-windows.yml:287-315` 已在发布端验证 SHA-256，并上传 `.sha256`；但客户端完全没有消费这份安全信息。
- `docs/GitHub发布更新说明.md:72-73` 明确记录当前安装包未配置 Authenticode，客户端仍以名称和大小判断。

可见后果：

- 同名同大小的缓存替换可以绕过现有判断。
- `QSettings` 中 pending 路径被本机其他进程篡改后，可指向同名恶意文件。
- 下载完成到 UAC 执行之间存在检查后替换窗口。
- 一旦 GitHub 账号、Release、CDN 链路、本机缓存目录或设置被利用，恶意程序会得到管理员权限。

立即止血：

1. 在可信校验上线前关闭“下载完成后自动安装”，只提示用户并打开可信 Release 页面。
2. pending 只允许位于应用专用更新目录内，拒绝外部路径和符号链接/重解析点。

正式修复：

1. 从 Release 精确匹配 `.sha256` 或 asset digest，下载后、缓存复用时和 UAC 前都重新计算 SHA-256。
2. 为公共 Windows 发布增加 Authenticode 和 RFC 3161 时间戳；客户端固定允许的发布者证书身份或公钥。
3. 校验下载 URL 必须为 HTTPS 且属于允许的 GitHub/CDN 主机。
4. 用安全暂存与原子替换缩短 TOCTOU 窗口。

验收标准：

- 安装包修改任意 1 字节后，在出现 UAC 前被拒绝。
- 同名同大小伪造文件、缓存外路径和错误发布者都被拒绝。
- 正确签名包可以完成真实旧版本到 Latest 的升级。

## 4. P1 高风险问题

### P1-01 跨项目后台任务会污染同号任务，并同步错误项目的全局索引

**类型：当前工作树中确定的逻辑缺陷，尚未由当前源码构建验证。**

触发链路：

1. 项目 A 创建任务 `jobId=N` 后启动后台工作。
2. 用户切换到项目 B。
3. `AppContext.cpp:154` 调用 `JobEngine::reloadJobs()`；`JobEngine.cpp:121-176` 清空内存并按 B 的数据库重建任务，数字 ID 会在各项目中重复。
4. A 的后台线程只把 `jobId` 排队给全局单例 `JobEngine`，例如 `MediaTaskService.cpp:516-543`、`MetadataExtractionService.cpp:307-326`、`MaterialCatalogSyncService.cpp:1184-1211`、`VideoAnalysisService.cpp:3328-3364`。
5. `JobEngine.cpp:220-240` 始终写“当前项目数据库”。

后果：

- B 恰好有同号任务时，A 的进度、成功或失败会覆盖 B 的任务状态。
- B 没有同号任务时，A 的更新被静默丢弃，A 的历史任务永久停留或消失。
- 媒体/元数据完成信号不携带项目路径；切换后 `syncCurrentProject()` 会同步 B，而不是发生变化的 A，造成 A 的全局搜索索引滞后。
- UI 可能显示错误素材、错误进度和错误失败原因，用户难以判断实际处理结果。

修复方向：

- 任务标识必须包含 `projectDatabasePath/projectUuid + jobUuid`，不能只传项目内自增数字。
- `JobEngine` 更新接口必须验证项目上下文，并直接写任务所属数据库。
- `catalogChanged` 事件携带项目路径；全局同步服务按事件项目同步。
- 增加 A→B 切换、同 ID 冲突和 A→B→A 三组并发测试。

### P1-02 媒体任务缺少活动键去重，恢复和扫描完成可启动重复 worker

**类型：当前工作树中的确定性竞态。**

证据：

- `MediaTaskService.cpp:67-128` 查询待处理数量后直接创建任务和 `QtConcurrent::run`，没有 `activeKey/QSet`。
- `MediaTaskService.cpp:130-159` 项目打开时为所有 `ok/warning` 素材源排队调用 `startForSourceRoot()`。
- `AppContext.cpp:160-167` 同时启动恢复扫描，并在扫描完成后再次调用 `startForSourceRoot()`。
- 对照 `MetadataExtractionService.cpp:83-89`，该服务已经使用项目路径和素材源组成活动键；媒体任务没有同等保护。

后果：

- 同一素材源可同时运行两套缩略图和媒体探测。
- 两个 worker 可能同时写同一个缩略图缓存路径、重复调用 FFmpeg/探测器，并争用 SQLite。
- 任务栏出现重复任务、进度互相覆盖，失败/成功统计失真。
- 项目打开后若恰有中断扫描，恢复媒体任务可能先处理旧目录快照，再被扫描完成事件再次启动。

验收标准：

- 同一 `project + sourceRoot + workType` 任意时刻最多一个活动 worker。
- 项目恢复和扫描完成同时触发时只产生一组任务。
- 压力测试中同一缩略图文件没有并发写入。

### P1-03 后台 future 被丢弃，退出或自动更新时存在对象释放后访问

**类型：已确认的生命周期设计缺陷。**

使用 `QtConcurrent::run([this])` 且未保存/等待 future 的位置包括：

- `MaterialCatalogSyncService.cpp:1065`、`1118`
- `MediaTaskService.cpp:124`
- `MetadataExtractionService.cpp:111`
- `VideoAnalysisService.cpp:2021`、`2375`
- `SettingsViewModel.cpp:575`

这些任务会继续访问 service、数据库管理器、JobEngine、视觉客户端或通过 `invokeMethod(this, ...)` 回到对象。除 `ScanEngine` 使用 `QFutureSynchronizer` 外，没有统一关停屏障。

后果：

- 用户退出、安装更新自动退出或对象析构时，worker 可能访问已释放的 `this` 或依赖对象，导致崩溃、堆损坏或数据库连接异常。
- 后台写入可能在应用退出阶段被截断，状态停在 running。
- 自动安装当前会在 500ms 后直接退出，进一步放大该窗口。

修复方向：

- 所有长期任务归入统一生命周期管理器，保存 future、支持取消，并在依赖对象析构前等待安全点。
- worker 捕获不可变值或受控共享状态，避免裸 `this`。
- 增加导入、视觉分析、全局同步和连接测试进行中退出的压力测试。

### P1-04 删除项目的边界验证不足，可能把数据库所在整个目录移入回收站

**类型：已确认的破坏性路径风险。**

证据：

- `ProjectService.cpp:20-26` 对文件输入直接把任意文件绝对路径视为项目数据库路径。
- `ProjectService.cpp:529-570` 只要能读出 `project` 表，就把数据库所在目录作为 `projectRoot`。
- `ProjectService.cpp:546-553` 对整个目录调用 `QFile::moveToTrash(projectRoot)`。
- 没有验证文件名必须为 `project.cvdb`、目录必须是专用项目根、记录的根路径必须与物理目录一致，也没有项目清单标记。

后果：

- 一个被放在“文档”等普通目录里的有效 `.cvdb`，从项目库删除时可能把整个普通目录移入回收站。
- 若回收站空间或卷行为异常，恢复成本很高。

验收标准：

- 删除前验证规范文件名、项目标记、物理根和记录根一致。
- UI 明确展示将被移动的绝对目录并二次确认。
- 对非专用根目录拒绝整目录删除，只允许从项目库移除记录。

### P1-05 项目创建、打开、改名和移动缺少事务与文件系统回滚

**类型：已确认的数据一致性问题。**

证据：

- `ProjectService.cpp:129-176`、`572-593` 先 `DELETE FROM project` 再插入，没有事务；插入失败会留下空项目记录。
- `ProjectService.cpp:231-263` 先创建目录、打开数据库、写设置和当前项目；任一步失败没有完整回滚。
- `ProjectService.cpp:262-263` 创建项目时 Logger 初始化失败会返回 false，但项目已成为当前项目且数据库仍打开。
- `ProjectService.cpp:302-316` 打开项目时信任数据库里的 `root_path`；Logger 失败同样会留下已打开但未发出 `projectChanged` 的状态。
- `ProjectService.cpp:412-425`、`500-512` 已完成目录改名/移动后，如果目录补全或数据库记录更新失败，不会把目录移回原位。

可见后果：

- UI 报告创建/打开失败，但内部实际上已经切换项目。
- 项目库、数据库记录、物理目录和全局索引互相不一致。
- 用户在资源管理器中移动项目后再打开，旧 `root_path` 会被重新创建，缓存、日志和分析文件分裂到旧/新两个位置。
- 磁盘满、权限变化或杀毒软件拦截时尤其容易出现半完成状态。

修复方向：

- 数据库记录使用显式事务。
- 项目操作实现“准备、提交、回滚”状态机，并记录恢复日志。
- 打开项目时以数据库实际所在目录为可信物理根；记录根不一致时提示修复或只读打开。
- 为每个失败点做故障注入测试。

### P1-06 可恢复扫描会发布过时检查点，且一个不可访问子目录可永久阻塞素材源

**类型：新扫描架构中的确定性边界缺陷。**

已经确认的改进：旧版“先删可见目录和素材、再重建”的数据丢失链路已改为暂存表加最终事务，见 `ScanEngine.cpp:1160-1268`。

剩余问题：

- `ScanEngine.cpp:193-217` 恢复时只把 `running` 工作项退回 `pending`；已 `completed` 的目录不会重新枚举。
- `ScanEngine.cpp:982-1055` 每个目录枚举一次后即标记 completed。
- 扫描中断到恢复期间，已完成目录内新增、删除或修改的文件不会更新暂存结果；最终 `1160-1228` 仍会把旧暂存快照发布为当前目录。
- `ScanEngine.cpp:944-946` 遇到一个不可访问目录就抛异常；该目录仍为 pending，下一次恢复会再次命中同一目录。
- `ScanEngine.cpp:884-889` 每次失败都增加 warning_count。

后果：

- 恢复扫描可能漏掉新增文件、保留已删除文件或保留旧大小/修改时间。
- 一个被权限保护、临时离线或损坏的子目录可让整个素材源无限“恢复—失败”，新目录永远无法发布。
- warning_count 持续增加，状态噪声掩盖真正问题。

修复方向：

- 恢复前验证已完成目录的目录指纹，变化时回退为 pending；或明确采用一次性 generation 并在恢复前重建暂存。
- 不可访问子目录记录为 warning 并跳过，除非根目录本身不可访问。
- 为“中断后目录变化”和“单个受保护子目录”增加故障注入测试。

### P1-07 本地搜索助手真实查询稳定返回无效 JSON，且发布 CI 排除了该测试

**类型：已实际复现的功能故障。**

复现结果：

- 直接运行该测试并保存详细输出，连续 3 次均为 `7 passed, 2 failed`。
- 稳定失败用例：
  - `understandsRedDenimJeans`
  - `understandsPictureAsFramesAndKeepsBothRequiredEntities`
- 两者都失败于 `result.has_value()`，错误为“本地查询助手返回无法解析：视觉接口返回内容不是有效 JSON”。
- `SearchAssistantClient.cpp:317-332` 使用 256 `max_tokens` 和 JSON Schema 请求；`345-351` 解析失败后直接降级。
- `.github/workflows/release-windows.yml:227` 排除 `gpu-integration`；`CMakeLists.txt:855-858` 正好给该测试打了此标签。

后果：

- 需要颜色/材质组合、图片帧和多实体约束的查询无法获得模型增强。
- `MaterialCenterViewModel.cpp:1224-1233` 会把失败缓存 120 秒，短期内重复查询也不会重试。
- 发布流水线仍为绿色，真实模型回归可以进入正式 Release。

根因范围：

- 已确认不是“模型资产不存在”或“GPU 不可用”；测试中模型启动、GPU 检测和另一条日期/地点查询均成功。
- 根因已收敛到模型输出截断、Schema/llama-server 兼容或响应解析之间；当前没有保留失败原始响应，仍需增加脱敏诊断后定案。

验收标准：

- 三条真实查询连续运行至少 20 轮均返回可校验的 V2 JSON。
- 截断或非法 JSON 时有一次受控修复/重试，不产生搜索结果污染。
- 正式发布必须运行同一模型资产的最小真实推理门禁。

### P1-08 更新策略与界面语义不符合约定，自动安装会无确认退出；手动代理会偷偷回退直连

**类型：已确认的产品语义和网络边界问题。**

现象：

- 项目约定要求“自动更新 / 手动更新 / 禁止更新”三态；当前没有 `UpdatePolicy`，只有代理网络三态和 `autoInstallUpdates` 布尔值。
- `SettingsPage.qml:257-275` 把开关标题写成“自动更新”，实际文案却是“下载完成后自动安装/询问”。
- `UpdateService.cpp:409-435` 每次启动都会检查并下载更新，用户没有“仅手动检查”或“禁止联网”的选择。
- `SettingsViewModel.cpp:107-116` 开关打开后，下载完成直接调用安装，不显示“立即更新 / 下次启动更新”确认。
- `UpdateService.cpp:624-625` 更新会话启动后 500ms 直接退出应用。
- `UpdateService.cpp:476`、`773` 对任意非空代理都允许直连回退；手动代理失败后也会执行 `retryCheckWithoutProxy()` / `retryDownloadWithoutProxy()`。

后果：

- 默认启动检查会在用户不知情时下载当前约 732 MiB 的安装包。
- 开启“自动更新”的用户会在下载完成时突然退出当前程序，正在运行的扫描/分析任务被中断。
- 选择手动代理的企业或隐私场景仍可能绕过代理直接连接 GitHub，违反用户明确网络边界。

修复方向：

- 独立实现更新策略三态，默认 automatic；网络模式仍保持独立三态。
- automatic 只负责自动检测/下载，下载完成仍显示两个按钮；不要把它等同于无提示安装。
- manualProxy 模式失败时必须失败关闭，不得直连；只有 automaticProxy 可回退直连。
- 覆盖 3×3 九种策略/网络组合测试。

### P1-09 大安装包在慢速网络上无法完成，失败后从零开始；更新缓存已实际膨胀到 5.079 GiB

**类型：已确认的更新可靠性和磁盘资源问题。**

证据：

- GitHub v0.1.177 安装包大小为 767,813,714 字节，约 732 MiB。
- `UpdateService.cpp:793-801` 使用 curl，固定 `--max-time 600`。
- 在 600 秒内完成当前安装包需要持续约 1.22 MiB/s（约 9.8 Mbit/s）；低于该速度的用户必然超时。
- `UpdateService.cpp:787` 每次开始下载先删除 `.part`；`948-981` 失败也删除 `.part`，没有断点续传。
- 没有 `QStorageInfo`、可用空间检查或下载/安装空间预算。
- `UpdaterSession.cpp:222-304` 为每次更新复制一份临时运行时；`577-601` 成功后没有清理 installer、staging 或 session。
- 本机只读统计：更新目录 5708 个文件、5.079 GiB；其中 7 个旧安装包 3.68 GiB、5 个 staging 目录 1.39 GiB、9 个 session 目录。

后果：

- 慢速、抖动或高延迟代理网络永远无法完成更新，每次启动重新消耗流量。
- 多次更新持续占用系统盘，最终导致下载失败、SQLite 写入失败或安装中途磁盘不足。
- 用户无法在界面中识别和清理更新缓存。

修复方向：

- 使用可续传下载、合理的空闲超时而不是固定总时限，并校验 Range/ETag。
- 下载前计算安装包、暂存、安装和回滚所需空间，空间不足时拒绝开始。
- 新版成功启动后清理旧安装包、成功 staging 和过期 session；失败只保留最近一次有诊断价值的内容。
- 设置总量和保留数量上限。

### P1-11 反馈服务附件无鉴权，上传和登录缺少资源/速率边界

**类型：一部分已确认、一部分为部署配置触发的高风险。**

证据：

- `main.py:949-955` 附件下载路由不验证客户端或管理员令牌。
- `main.py:733-751` 对每个附件执行 `await upload.read()`，完整读入内存后才检查 100MB。

- 附件使用会话鉴权或短时签名 URL。

- 数据库提交与文件原子改名组成可回滚流程。
- 管理密码缺失或仍为默认值时拒绝启动；增加 IP/账号速率限制和审计。
- 收敛 CORS 到实际管理端域名。

### P1-12 客户端保存附件会先删除旧文件，并忽略写入失败

## 5. P2 中风险问题

### P2-01 VideoAnalysisService 删除仍被活动句柄引用的数据库连接

- `VideoAnalysisService.cpp:2032-2051`、`2380-2417` 的完成 lambda 在局部 `QSqlDatabase db` 仍存活时调用 `closeThreadConnection()`。
- 正常结束路径 `3184` 也有同样问题。
- `GlobalDatabaseManager.cpp:291-300` 最终调用 `QSqlDatabase::removeDatabase()`。

Qt 要求移除连接前销毁所有该连接的 `QSqlDatabase/QSqlQuery` 句柄。违反后会产生 warning、使现有查询失效，严重时造成后续数据库操作异常。当前媒体、元数据和全局同步代码已经通过 `db = QSqlDatabase()` 修复了相同模式，视频分析尚未统一。

### P2-02 A→B→A 搜索切换会让当前 A 永久停在本地基线结果

- `MaterialCenterViewModel.cpp:1183-1188` 如果 A 已在 in-flight，回到 A 时不启动新任务。
- 旧 A 完成后，`1212-1221` 先移除 in-flight，再因 generation 不匹配直接丢弃。
- 缓存写入在 `1251-1263`，位于丢弃判断之后。

因此 A 发起、切到 B、再切回 A 时，旧 A 结果被丢弃，而当前 A 又没有新任务或缓存可用。后果是界面一直显示本地基线，直到用户再次改变查询。

### P2-03 本地搜索启动/停止在 UI 线程做最长数秒同步等待

- `LocalSearchAssistantRuntime.cpp:40-65` GPU 探测最多同步等待约 9 秒。
- `150-210` 的 `start()` 直接调用探测。
- `MaterialCenterViewModel.cpp:1189-1198` 在搜索 UI 路径直接调用 `start()`。
- `LocalSearchAssistantRuntime.cpp:213-227` 停止时同步等待最多约 2.5 秒。

后果是首次搜索、空闲卸载、退出或模型异常时出现明显卡顿或“未响应”。应把探测、启动和停止做成异步状态机。

### P2-04 新任务历史只持久化部分字段，SQL 失败被静默忽略

- `DatabaseManager.cpp:343-354` 的 job 表只有基本字段和 `source_root_id`。
- `JobEngine.cpp:145-176` 重载时只能重建素材源 subject，项目、素材、帧、路径和 `JobProgressContext` 全部丢失。
- `JobEngine.cpp:133-143` 标记中断任务时忽略 `exec()` 返回值。
- `JobEngine.cpp:220-240` 持久化也不检查执行结果。

后果是重启后的任务详情、跳转对象和分步进度缺失；数据库锁定或磁盘满时 UI 仍显示已保存，实际重启后任务消失。还缺少历史分页/上限，长期运行会持续加载全部任务。

### P2-05 QML 静态检查仍有大量告警和未定义布局行为

当前 33 个 QML 文件的 `qmllint` 结果：

- 746 条诊断：741 warning、5 info。
- 20 个文件未通过 lint。
- 697 个 unqualified、25 个 import、7 个 incompatible-type、6 个 missing-property、5 个 layout undefined。

较值得优先处理的位置：

- `MaterialCenterWorkspace.qml:1278,1985`
- `JobProgressInspectorPane.qml:238`
- `SettingsPage.qml:219,1044`
- `InspectorPane.qml:55`
- `AssetPreviewOverlay.qml:260`
- `MaterialCenterWorkspace.qml:1601-1602`
- `SettingsPage.qml:1104`
- `AssetPreviewOverlay.qml:137-138`
- `QuickSearchWindow.qml:187,481-492`

其中多个 `MiddleDragScrollHandler.flickable` 把静态类型为 `QQuickItem` 的 `ScrollView.contentItem` 绑定给 `QQuickFlickable`，以及 Layout 管理元素同时写 width/height，行为依赖 Qt 实现细节。短期至少应建立“告警不增加”门禁，随后清零 incompatible-type 和 layout undefined。

### P2-06 日志没有轮转，并存在同步 I/O 和跨线程共享状态

- `AppBootstrap.cpp:26-35` 每条 Qt/QML 消息都重新打开 `qml-startup.log` 追加。
- `57-83` 安装的是全运行期全局 message handler，不只是启动阶段。
- `Logger.cpp:10` 使用无锁全局 `QString g_logFilePath`。
- `Logger.cpp:57-69` 每条日志都同步打开文件写入，没有轮转、大小上限或保留期。
- 视觉网络 worker 会写 Logger，而项目切换会重设全局日志路径，存在数据竞争和跨项目日志错位。

后果包括日志无限增长、频繁磁盘 I/O、并发日志交错、切换项目时写错日志文件，以及极端情况下 QString 数据竞争。

### P2-07 版本回退值仍停在 v0.1.97，开发构建与正式版本容易漂移

- `CMakeLists.txt:3` 默认项目版本为 0.1.97。
- `installer/windows/cinevault.iss:1-6` 默认 AppVersion/VersionTag 也是 0.1.97。
- 正式脚本会正确注入版本，因此 v0.1.177 Release 本身一致；但任何绕过脚本的本地/临时构建都会显示和打包为旧版本。

建议把版本唯一来源集中到一个机器可读文件，CMake、安装器、运行时和发布脚本都读取它；CI 再验证注入后的最终二进制。

### P2-08 代理凭据进入 QSettings 和 curl 命令行

- `AppSettings.cpp:465-472` 明文保存手动代理 URL。
- `UpdateService.cpp:57-63` 把完整代理 URL 作为 curl 的 `--proxy` 参数。
- `UpdateService.cpp:283-313` 会把用户名和密码编码进 URL。

后果是代理密码可能出现在设置文件、进程列表、崩溃转储和诊断工具中。应使用系统凭据存储，并尽量通过受保护配置或 stdin 传递，日志只显示代理类型和主机，不显示用户信息。

### P2-09 CI 和测试门禁覆盖不完整

- Windows Release CI 排除了唯一真实模型 GPU 集成测试。
- workflow 的 `paths-ignore` 排除了 `services/**` 和 `tools-web/**`，仓库中又没有其他 workflow，因此反馈服务、赞助后端和网站改动没有任何自动 CI。
- Release CI 只运行 CTest，不运行三个 Python 测试集和 `qmllint`。
- 当前新增的 `MaterialCenterUiContractTest` 主要通过搜索源码字符串验证连接方式，不能替代并发运行时测试。
- 当前 15 个未提交文件晚于测试二进制约 8.5 小时，本轮遵守要求没有本地编译，所以这些改动仍处于“静态审计通过/未通过混合、可编译性未知”状态。
- 本机没有 `actionlint`；YAML 可解析，但缺少 Actions 专项 lint。

建议拆分桌面 Release、服务端 CI、网站 CI，并把静态检查、Python 测试、跨项目并发、退出压力和最小真实模型推理纳入门禁。
