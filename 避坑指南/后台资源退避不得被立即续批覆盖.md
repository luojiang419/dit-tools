# 后台资源退避不得被立即续批覆盖

## 问题表现

- 任务长期停留在“准备处理 0/N”。
- 日志按固定短周期不断创建同类任务。
- 每次任务都显示已安排退避，但实际很快再次执行。
- 待办数量长期不下降，旧失败任务又被替代任务清理。

## 根因

子任务失败路径已经安排较长退避，但外层批次调度器忽略子任务结果，又无条件安排
更短的立即续批。若定时器采用“更早者优先”，短定时器会替代真正的退避。

```text
子任务：失败 -> 5 秒后重试
外层：无条件 -> 250 ms 后续批
合并结果：250 ms 生效，5 秒退避失效
```

## 修复原则

1. 重试定时器必须只有一个明确责任方。
2. 外层只在子任务正常完成时安排立即续批。
3. 子任务已失败、取消或安排退避时，外层不得再覆盖。
4. 回归测试要观察“短时间内没有创建替代任务”，不能只验证最终会重试。
5. 任务失败原因在替代任务真正创建前必须保持可见。

## 本项目回归方法

- 占用 Heavy I/O 资源，让元数据任务进入等待。
- 通过 generation 变更取消等待。
- 验证任务显示“已安排自动重试”。
- 在小于首档退避、但大于立即续批的窗口内检查任务总数仍为 1。
