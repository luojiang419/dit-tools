# 数据库版本已升级但表列缺失的幂等修复

## 现象

项目库 `schema_version` 看起来已经到新版本，但运行时 SQL 报：

```text
no such column: next_retry_at
```

这类问题常出现在：

- 某次迁移中途失败但版本号或部分表结构已变化；
- 新代码查询了新增列，但旧表没有被幂等补齐；
- 兼容函数里先创建依赖新增列的索引，再执行 `ALTER TABLE ADD COLUMN`。

## 这次的根因

`ensureMediaSchemaCompatibility()` 在旧 `media_metadata` 表上先执行：

```sql
CREATE INDEX IF NOT EXISTS idx_media_metadata_retry
ON media_metadata(probe_status, next_retry_at, retry_policy_version, asset_id)
```

旧表还没有 `next_retry_at`，所以索引创建失败，事务回滚，后续补列没有发生。

## 正确顺序

兼容迁移必须按这个顺序写：

1. `CREATE TABLE IF NOT EXISTS` 创建缺失表。
2. 只创建依赖旧列或必定存在列的索引。
3. `PRAGMA table_info` 检查列是否存在。
4. `ALTER TABLE ADD COLUMN` 幂等补列。
5. 最后创建依赖新增列的索引。

## 测试要求

不要只测“低版本库升级”。还要测：

- `schema_version = 当前版本`，但表列缺失；
- `schema_version = 上一版本`，但表结构部分升级；
- 旧数据在补列后仍保留；
- 新增索引确实存在；
- 迁移失败时事务回滚。

## 本次覆盖

新增 `FolderDatabaseMigrationTest::projectMetadataRetryColumns_repairFromV9AndCurrentSchema()`：

- 构造旧 `media_metadata` 和 `embedded_metadata`；
- 分别模拟 `schema_version = 9` 与 `schema_version = CurrentSchemaVersion`；
- 验证 retry 列、retry 索引和旧数据。

## 以后避坑

凡是新增列并同步新增索引，必须先补列再建索引。尤其是 `CREATE INDEX IF NOT EXISTS` 不是“安全万金油”：索引名不存在时，SQLite 仍会校验被索引列是否存在。
