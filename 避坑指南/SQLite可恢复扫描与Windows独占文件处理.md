# SQLite 可恢复扫描与 Windows 独占文件处理

## 现象

- 扫描磁盘卷时任务失败，详情显示 `database is locked 无法取行` 或 `无法获取行`。
- Windows 上某个素材被其他软件以独占方式打开时，仅检查 `QFileInfo::isReadable()` 仍可能得到可读，但真正打开文件会失败。
- 扫描失败后，任务状态保存也会继续与扫描写事务竞争，于是日志可能每隔数秒重复出现数据库锁错误。

## 根因

1. 可恢复扫描从 SQLite 读取下一目录后，没有在开启写事务前主动结束查询游标。WAL 模式下，带活动读快照的连接升级为写事务可能产生 `SQLITE_BUSY`。
2. 目录枚举、文件元数据读取和文件可打开性探测原本位于数据库写事务内部。慢磁盘、海量目录或被占用文件会不必要地延长写锁持有时间。
3. `QFileInfo::isReadable()` 主要反映权限属性，不能证明当前进程此刻能够打开文件；独占共享模式、杀毒软件或素材软件锁定仍会让实际打开失败。

## 修复模式

- 读出单条目录记录后立刻调用 `QSqlQuery::finish()`，再开始该目录的写事务。
- 在写事务外完成目录枚举和 `QFile(QIODevice::ReadOnly)` 探测，只把已经整理好的轻量记录批量写入 SQLite。
- 对实际无法打开的文件保留索引记录，但写入 `is_readable = 0`；素材同步时把它标记为不可用，因此缩略图、元数据和视觉解析队列会自动跳过。
- 后续重新扫描时再次探测；文件解锁后自动恢复为 `is_readable = 1`，无需删除并重新添加磁盘卷。
- 聚合查询读完结果后同样调用 `finish()`，避免随后事务继承活动读快照。

## 不要采用的替代方案

- 不要只把 `PRAGMA busy_timeout` 从 5 秒大幅提高。它只能把报错变成长时间卡顿，不能消除活动游标升级和超长写事务的根因。
- 不要因为一个文件打不开就中止整个磁盘卷扫描。
- 不要把不可读文件永久删除出索引，否则文件解锁后无法通过普通重扫自然恢复。

## 回归验证

- Windows 测试用 `CreateFileW(..., shareMode = 0)` 独占锁定 MP4。
- 第一次扫描应成功结束，文件 `is_readable = 0`，卷状态为警告而不是失败。
- 释放句柄后重扫，文件应恢复为 `is_readable = 1`，警告计数归零。
- 同时执行素材目录同步测试，确认不可读文件不会进入图片/视频解析链路。
