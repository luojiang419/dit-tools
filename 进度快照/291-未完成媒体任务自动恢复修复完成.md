## 已完成内容

- 确认应用启动后已经触发自动恢复；卡住不是缺少启动入口，而是失败缩略图被错误地无限重试。
- 修复缩略图自动恢复筛选：

  - 自动重试异常退出遗留的 `Running` 素材；
  - 自动修复状态为 `Success` 但缓存路径为空的异常记录；
  - 不再自动重试终态 `Failed` 素材。
- 计数 SQL 和分页取数 SQL 使用同一套状态规则，避免任务总数与实际执行数不一致。
- 增加 `media_task_dispatch` 日志，启动恢复时记录素材源、待处理元数据数量和待处理缩略图数量。
- 新增自动恢复回归测试，验证失败项保持终态，中断项和缺失项会自动完成。
- 根版本从 `0.1.183` 递增到 `0.1.184`。

## 根因证据

- 日志在 11:40:37 显示应用重新启动，11:40:40 打开 `服装数据库`，11:40:41 创建元数据和缩略图任务；说明自动恢复入口已经执行。
- 旧 SQL 使用 `thumbnail.status <> Success OR image_path = ''`，因此所有 `Failed` 记录都会再次进入恢复队列。
- 真实项目旧逻辑统计缩略图候选项为 37,638，其中 35,216 项是终态失败记录。
- 修复后的真实项目只读统计为 2,422 个可恢复缩略图，另有 2,421 个待处理元数据。
- 失败素材集中在损坏或历史乱码路径视频；FFmpeg 单文件最长等待 60 秒。每次启动从最小素材 ID 重新处理这些失败项，导致真正缺失的新素材长期无法执行。
- 媒体任务按“缩略图后元数据”串行，因此缩略图被无限失败重试阻塞时，元数据卡片始终为 0；全局索引并行分页写库时，三张卡片共同形成卡住观感。

## 代码前后对比

### 修改前

```sql
AND (
    thumbnail.asset_id IS NULL
    OR thumbnail.status <> Success
    OR COALESCE(thumbnail.image_path, '') = ''
)
```

该条件把 `Failed` 当作未完成任务，应用每次启动都会无限重试。

### 修改后

```sql
AND (
    thumbnail.asset_id IS NULL
    OR thumbnail.status IN (Pending, Running)
    OR (
        thumbnail.status = Success
        AND COALESCE(thumbnail.image_path, '') = ''
    )
)
```

`Failed` 成为真正终态；异常退出遗留的 `Running` 和没有记录的素材仍会自动执行。
